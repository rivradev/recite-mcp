## Bug #1 — CRITICAL: 7 MCP tools registered in server.py not exposed to MCP client

**Severity:** Critical — 7 tools (T35, T36–T39, T45–T46 of E2E plan) completely untestable.

### Affected Tools (not visible to MCP client)

| Tool | Test | Purpose |
|------|------|---------|
| `update_rule` | T35 | Enable/disable automation rules |
| `get_categories` | T36 | List default + custom categories |
| `create_category` | T37 | Add a custom category |
| `delete_category` | T45 | Remove a custom category (cleanup) |
| `get_vendors` | T38 | List custom vendors |
| `create_vendor` | T39 | Add a custom vendor |
| `delete_vendor` | T46 | Remove a custom vendor (cleanup) |

### Evidence

All 7 tools are:
- Registered in `src/recite_mcp/server.py` (lines 355–413)
- Implemented in `src/recite_mcp/tools.py` (lines 295–313)
- Implemented in `src/recite_mcp/api_client.py` (lines 397–424)

Confirmed via direct MCP protocol test: the server **does** return all 40 tools in its
`tools/list` response:

```bash
printf '<initialize>\n<tools/list>\n' | uv run recite-mcp
# → "Total tools in tools/list response: 40"
```

`ToolSearch` returns **"No matching deferred tools found"** for every one of them —
the Claude Code **client** had a stale cached tool list from when the session was first
established, before these 7 tools existed.

### Root Cause (confirmed)

**Stale MCP tool-list cache in Claude Code.** Claude Code queries `tools/list` once
when it connects to an MCP server (on startup or first use). The `/clear` command
resets the conversation history but does **not** re-query `tools/list`. If the 7 tools
were added to `server.py` after the session was first opened, they will not appear in
the deferred tool registry until Claude Code is fully restarted.

The server code and implementation are correct — no server-side changes are required.

### Fix

**User action (no code change needed):**
1. Quit Claude Code completely and reopen it.
2. Run `/mcp` to verify the `recite` server shows as connected.
3. All 40 tools will now appear in the deferred tool list.

**Documentation fix (already applied):**
- `CLAUDE.md` updated: "registers 33 tools" → "registers 40 tools + 3 resources".

## Bug #2 — MINOR: `list_memory` returns wrapped dict, not bare list

**Severity:** Low — functional, but mismatches documented return type.

### Observed

```json
{"result": [{"timestamp_utc": "...", "instruction": "...", "tags": [...]}]}
```

### Expected (per E2E plan and server.py type annotation)

```json
[{"timestamp_utc": "...", "instruction": "...", "tags": [...]}]
```

### Location

`server.py` line 434:
```python
@server.tool("list_memory")
def list_memory() -> list[dict]:
    return tools.list_memory()
```

### Root Cause

FastMCP wraps non-`dict` return values in a `{"result": ...}` envelope when the
annotated return type is not `dict`. The handler returns `list[dict]` which gets
wrapped.

### Fix

Change the return type and wrap manually:
```python
@server.tool("list_memory")
def list_memory() -> dict:
    return {"memories": tools.list_memory()}
```
Or if a bare list is desired, check FastMCP docs for how to return raw list responses.
Update the E2E plan assertion at T04 to match whichever shape is chosen.

## Bug #3 — MINOR: `process_receipt` rename silently overwrites existing files

**Severity:** Low — data-loss risk in specific scenario; a warning is emitted but no
abort/suffix option is provided.

### Observed (T11)

```
T11 called with rename=true on receipts/rename_test_raw.png
→ OCR extracted vendor="consult pro", date="2025-01-20", amount=2400.00
→ Target rename: receipts/2025-01-20_consultpro_2400.00.png
→ That file ALREADY existed in the receipts directory
→ Tool overwrote it silently and returned:
  "warnings": ["Renamed file overwrote an existing file at: 2025-01-20_consultpro_2400.00.png"]
```

The original file at `2025-01-20_consultpro_2400.00.png` was destroyed. In this run,
both files had the same content (both were copies of the same receipt), so no data was
actually lost. But in real usage, this could silently destroy a different receipt.

### Fix Options

1. **Append a counter suffix** when the target exists:
   `2025-01-20_consultpro_2400.00.png` → `2025-01-20_consultpro_2400.00_1.png`
2. **Return an error** and require the caller to pass `overwrite=True` explicitly.
3. At minimum, **demote warning to error** so callers cannot silently miss it.

### Affected Code

`src/recite_mcp/tools.py` — the rename logic inside `process_receipt`.
