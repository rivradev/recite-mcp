## Bug #1 — Missing API Key Scopes: `preferences:read` / `preferences:write`

**Severity:** High — blocks 4 tools and all of Phase 10
**Affected tools:** `get_categories` (T36), `create_category` (T37), `get_vendors` (T38), `create_vendor` (T39), `delete_category` (T45), `delete_vendor` (T46)

**Error responses:**
```
get_categories  → "API key lacks required scope: preferences:read"
get_vendors     → "API key lacks required scope: preferences:read"
create_category → "API key lacks required scope: preferences:write"
create_vendor   → "API key lacks required scope: preferences:write"
```

**Root cause:** The API key stored in `.mcp.json` does not have `preferences:read` or `preferences:write` scopes granted.

**To fix:**
1. Go to https://recite.rivra.dev/settings/api
2. Regenerate or create a new API key with all scopes enabled, including `preferences:read` and `preferences:write`
3. Update the `RECITE_API_KEY` value in `.mcp.json`

**Impact on cleanup:** `delete_category` (T45) and `delete_vendor` (T46) are also blocked — if Phase 10 is ever run with a correct key, those cleanup steps will need to be run manually or re-verified.

## Bug #2 — `process_receipt` with `rename=true`: Ledger Entry Written Even When Rename Fails

**Severity:** Medium — inconsistent behavior, data integrity risk
**Affected tool:** `process_receipt` (T11)
**Observed in:** T11 first attempt

**Reproduction steps:**
1. Call `process_receipt` with `rename=true` on a receipt whose computed rename target already exists in the directory
2. Observe: returns `status: "error"` but `ledger_entry` is populated and written to disk

**Actual response (first T11 attempt):**
```json
{
  "status": "error",
  "message": "Cannot rename: destination already exists: 2026-03-20_WholeFoodsMarket_62.84.png",
  "ledger_entry": {
    "entry_id": "a666ecc2-4458-47f3-8cbc-1456cfe76dfd",
    "entry_type": "receipt",
    "vendor": "Whole Foods Market",
    ...
  }
}
```

**Expected behavior (two acceptable options):**
- **Option A (atomic):** Do not write the ledger entry if rename fails. Return `status: "error"` with `ledger_entry: null`. The operation is all-or-nothing.
- **Option B (partial):** Write the ledger entry, rename the file, return `status: "ok"` with `renamed_to: null` when rename fails (non-fatal). The rename failure is surfaced as a warning, not an error.

**Current behavior is a hybrid of both:** ledger entry written (like Option B) but `status: "error"` (like Option A) — this is the worst of both worlds.

**Fix location:** `src/recite_mcp/tools.py` — `process_receipt` method. The ledger write should either be conditioned on rename success, or the status/message should be changed to `"ok"` / `"processed_rename_failed"` when the receipt data was extracted successfully but only the rename step failed.

**Secondary issue — rename collision not pre-checked:** The tool attempts the rename and only discovers the collision after processing. A preflight check (`os.path.exists(target_path)`) before scanning would allow returning an early error without writing a ledger entry.

## Observation — Leftover Test Artifact from Previous Run

**Not a code bug, but a test plan gap.**

**What happened:** `receipts/2026-03-20_WholeFoodsMarket_62.84.png` was present at the start of the run — it is a renamed output from a previous T11 run that was not cleaned up. This caused the first T11 attempt to fail with Bug #2.

**Root cause:** The E2E plan's fixture restore step (after T11) copies a receipt to `rename_test_raw.png` but does not delete the renamed output file. On the next run, that renamed file collides with the new rename attempt.

**Suggested fix to test plan (Phase 0-F):** Add a step to delete any `receipts/*.png` files whose name matches `YYYY-MM-DD_*` format AND whose date equals today's date from the Whole Foods receipt, or more specifically:

```
# Add to Phase 0-F cleanup:
Delete receipts/2026-03-20_WholeFoodsMarket_62.84.png if it exists
(or more generally: delete any file in receipts/ that was produced by a prior T11 rename)
```

Alternatively, add to the end of T11:
```bash
# After fixture restore, also remove the renamed output so the next run starts clean
rm -f receipts/$(date +%Y-%m-%d)_*.png   # caution: only rename_test output
```

## Observation — `export_transactions` Returns Object, Not Array

**Severity:** Low — documentation mismatch
**Affected tool:** `export_transactions` (T44, JSON format)

**Test plan says:** "Assert: returns JSON array or download URL"
**Actual response shape:**
```json
{
  "transactions": [...],   // 508 items
  "total_count": 508,
  "exported_at": "..."
}
```

The response is a JSON **object** wrapping the array, not a bare array. The test plan assertion should be updated to reflect the actual schema:

```
Assert: response is a JSON object with:
  - "transactions": array of transaction objects
  - "total_count": integer
  - "exported_at": ISO timestamp string
```

This is not a defect in the code — the shape is sensible — but the plan's assertion is inaccurate.
